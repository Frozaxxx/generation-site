# Generation Site

Панель, которая генерирует профиль вымышленной B2B-компании, а затем собирает на его основе сайт из трёх страниц.

> **Все компании, люди, адреса и телефоны вымышленные.** Это демонстрационный проект (тестовое задание).
> Телефоны берутся из блоков, которые Bundesnetzagentur зарезервировала для медиапроизводств («Drama Numbers»):
> они совпадают с кодом города, но не выдаются абонентам. Фото команды генерируются моделью.
> Сгенерированные регистрационные сведения не заменяют проверку юрлица в официальных реестрах.

Работа идёт в два этапа:

1. **Компания.** Параметры → генерация → карточка компании (JSON) → ручные правки → утверждение.
2. **Сайт.** Утверждённая карточка + язык (RU/DE) + оформление → версия сайта → предпросмотр и ZIP.

Повторная сборка сайта не генерирует факты заново: единственный источник фактов — сохранённая карточка конкретной ревизии.

## Основной стэк

- `Python 3.14`, `FastAPI`, `SQLAlchemy 2 (async)` + `Alembic`, `Pydantic 2`
- `SQLite` — проект запускается без Docker и внешних сервисов
- `LangGraph` — графы генерации компании и сборки сайта
- `OpenRouter` — тексты и фото команды
- `Jinja2` — шаблон генерируемого сайта, шрифты Fontsource (OFL) внутри сайта
- `React 18` / `TypeScript` / `Vite` / `Tailwind 4` / `Zustand` / `React Router 7` — панель

## Запуск

```bash
cd backend
cp .env.example .env          # вписать OPENROUTER_API_KEY
uv sync
uv run python main.py         # http://127.0.0.1:8000/docs
```

Миграции применяются автоматически при старте. Данные лежат в `backend/data/` (в git не попадают).

Панель:

```bash
cd frontend
npm install
npm run dev                   # http://localhost:5173, /api и /media проксируются на :8000
```

Через Docker (backend + панель):

```bash
cp backend/.env.example backend/.env   # вписать OPENROUTER_API_KEY
docker compose up -d --build           # панель http://localhost:3000, API http://localhost:8000/docs
```

Данные хранятся в volume `backend-data`.

### Проверка OpenRouter

Один дешёвый запрос: проверяет ключ, модель, разбор JSON и учёт стоимости.

```bash
uv run python -m src.cli check-openrouter                 # модель по умолчанию
uv run python -m src.cli check-openrouter --model openai/gpt-4.1-mini
uv run python -m src.cli check-openrouter --image         # + тестовое фото в backend/data/
```

Проверки:

```bash
uv run pytest
uv run ruff check . && uv run ruff format --check .
```

## Архитектура

Бэкенд разбит на модули, внутри модуля — слои:

```plain
backend/src/
├── core/                  # настройки, FastAPI, база, логирование, миграции
├── shared/                # общие базовые классы: сущности, ошибки, пагинация, репозиторий
├── llm/                   # клиент OpenRouter, лимит расходов, прайс моделей
├── jobs/                  # фоновые задачи генерации: этапы, прогресс, расходы
├── companies/             # этап А: компании и их карточки
│   ├── domain/            # сущность Company, карточка, каталог, проверки согласованности
│   │   └── catalog/       # страны, города, направления, масштабы
│   ├── application/       # сервисы, DTO, протоколы репозиториев
│   ├── infra/database/    # ORM-модели, мапперы, SQL-репозитории
│   ├── dependencies/      # сборка сервисов для FastAPI
│   └── api/v1/            # REST-ручки
├── sites/                 # этап Б: темы, шаблон, тексты и перевод, рендер, проверки, версии
│   ├── templates/site/    # один адаптивный шаблон: 3 страницы, CSS, sitemap, llms.txt
│   └── static/fonts/      # woff2 латиница + кириллица для тем
└── cli/                   # служебные команды: схема, проверка ключа, генерация, примеры
```

Правило зависимостей: `api → dependencies → application → domain`, `infra` реализует протоколы из `application`. Домен не знает про FastAPI и базу.

Панель — FSD, слой импортирует только слои ниже себя:

```plain
frontend/src/
├── app/        # точка входа, маршруты, глобальные стили и токены
├── pages/      # companies, company-new, company, site
├── widgets/    # app-shell, company-issues, company-sites
├── features/   # generate-company, edit-company-profile, build-site
├── entities/   # company, job, catalog, site
└── shared/     # requestJson, форматирование, UI-кит
```

### Генерация компании из терминала

```bash
uv run python -m src.cli generate-company --scale small          # с фото команды
uv run python -m src.cli generate-company --brand "Nordlicht" --no-photos
```

Та же операция доступна в API: `POST /api/v1/companies/generate`, прогресс — `GET /api/v1/jobs/{id}`.

## Как генерируется компания

1. **Факты выбирает код** (`companies/application/generation/facts.py`): город, улица и индекс из каталога, телефон из блока Drama Numbers этого города, домен и почта из названия бренда, год основания и число сотрудников по масштабу, состав команды (руководитель, 2 руководителя отделов, специалисты), имена из пулов разного происхождения, внешность для фото.
2. **Зёрна разнообразия**: история основания, отраслевой фокус, отличие, формат поставки и модель оплаты выбираются случайно. Модели передаются последние созданные компании, чтобы она не повторяла их нишу и формулировки.
3. **Тексты пишет модель** по графу LangGraph (`companies/application/generation/pipeline.py`):

   ```plain
   concept ─┬─ product ─┬─ assemble ─ review ─┬─ photos ─ save
            └─ team ────┘        ▲            │
                                 └── revise ◄─┘
   ```

   Продукт с FAQ и биографии команды пишутся параллельно, оба зависят только от концепции. Каждый ответ проверяется схемой (количество пунктов, длина, годы этапов, ровно те же люди).
4. **Смысловая проверка**: модель ищет противоречия в продукте, датах и обещаниях. Если найдены ошибки в продукте или слогане, граф делает один круг исправления и проверяет снова. Оставшиеся замечания показываются как предупреждения к той ревизии, которую проверяли.
5. **Фото**: общий офис компании, но у каждого своё место, поза, одежда и свет без повторов внутри команды; минимум двое каждого пола. Генерируются по 3 параллельно; лимит операции учитывает одновременные запросы через резервирование. При сохранении: кадр 4:5, 640×800, лёгкое зерно, JPEG без метаданных.

## Как собирается сайт

Сайт собирается только из **утверждённой** карточки, у каждого человека из команды должно быть фото. Граф LangGraph (`sites/application/pipeline.py`):

```plain
START ─┬─ copy ──────┬─ render ─ check ─ package
       ├─ translate ─┘    ▲
       └─ reuse ──────────┘
```

- **copy** — модель пишет только подачу: заголовки, подводки, title и description. Схема не пропускает числа, которых нет в карточке («200+ клиентов»), и требует название бренда в title каждой страницы.
- **translate** — для немецкой версии тексты карточки переводятся по путям четырьмя параллельными запросами. Перевод проверяется: те же ключи, те же числа, сохранены имена и латинские термины. Для русской версии тексты идут из карточки без изменений.
- **reuse** — если сайт этой ревизии на этом языке уже собирали, тексты берутся из него бесплатно, меняется только оформление.
- **render** — имена, адрес, телефон, почта, фото, год основания и состав команды шаблон берёт прямо из снимка карточки.
- **check** — проверки готовых HTML (см. ниже). Версия с ошибками сохраняется со статусом `failed_checks`.
- **package** — архив `<домен>-v<N>-<язык>.zip`, распаковал и открыл `index.html`.

Страницы: **Главная** (предложение, аудитория, проблема клиента, преимущества, шаги процесса, переход к продукту), **Продукт** (описание, входные данные и результат, процесс, формат поставки, ограничения, FAQ), **Компания и контакты** (история, этапы, специализация, команда с фото, контакты, выходные данные). Форм на сайте нет: связь по почте и телефону, о чём сайт прямо пишет.

Оформление: один шаблон и четыре темы (Kontor, Nordlicht, Mittelstand, Graphit) со своими шрифтами, палитрой и формой, плюс свой акцентный цвет.

### SEO, ИИ-поиск и скорость

- `title` с брендом и `meta description` на каждой странице, `canonical`, `meta robots`, Open Graph и Twitter Card с картинкой `og.png`, `theme-color`, favicon (SVG, PNG 32, apple-touch-icon).
- schema.org в JSON-LD: `Organization` (юрлицо, адрес, телефон, почта, `contactPoint`, основатель, год основания, число сотрудников) на всех страницах, `WebSite`, `WebPage`, `Service`, `FAQPage`, `AboutPage` с сотрудниками, `BreadcrumbList`.
- `sitemap.xml`, `robots.txt` с явным доступом для поисковиков и ИИ-краулеров (GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot, Google-Extended и др.), `llms.txt` с ключевыми фактами компании для ИИ-ассистентов.
- Семантика: один `h1` на странице, `nav`, `main`, `address`, `details` для FAQ, `alt` у фото, `lang` у страницы.
- Скорость: никаких внешних запросов. Шрифты лежат внутри сайта (woff2, латиница и кириллица, `font-display: swap`, preload основного начертания), CSS минифицирован, без JavaScript, фото 640×800 с размерами и `loading="lazy"`. Для немецких сайтов это ещё и вопрос GDPR: загрузка Google Fonts с серверов Google там известная проблема.

### Проверки сайта

Ошибки: нет страницы, `title`, description, favicon или `lang`; не один `h1`; нет ссылок на все страницы; битая внутренняя ссылка; картинка без `alt`; на странице нет юрлица, телефона, почты, адреса (факты сверяются на **всех** страницах); в title нет бренда; нет разметки `Organization` или телефон в ней другой; форма на сайте; обещание несуществующей функции («личный кабинет», «загрузите файл»); незаменённая переменная; кириллица на немецком сайте; нет сотрудника или его фото; нет `robots.txt`, `sitemap.xml`, `llms.txt`; API-ключ в любом файле. Предупреждения: длина title и description, нет `canonical` или `og:image`.

## OpenRouter

- **Ключ** задаётся только на сервере (`OPENROUTER_API_KEY` в `backend/.env`), хранится как `SecretStr`, в ответах API отдаётся только признак «задан / не задан». Фильтр логов и обработка ошибок вырезают ключ из любых сообщений.
- **Модель** выбирается из `OPENROUTER_ALLOWED_TEXT_MODELS`, цены подтягиваются из `GET /models` OpenRouter.
- **Ответы модели** проверяются pydantic-схемой. Невалидный ответ отправляется модели обратно со списком ошибок; это тоже попытка.
- **Повторы** ограничены `OPENROUTER_MAX_RETRIES`: сетевые сбои, 408/429/5xx — с паузой (учитывается `Retry-After`), 401/402/403 не повторяются.
- **Стоимость** берётся из `usage.cost` ответа OpenRouter, при отсутствии — считается по прайсу. Учитываются и неудачные попытки.
- **Лимит на операцию** (`OPENROUTER_OPERATION_BUDGET_USD`): перед каждым запросом проверяется, что потраченное плюс худший случай (входные токены + `max_tokens` по прайсу) укладываются в лимит.
- **Этапы генерации** сохраняются в таблицу `jobs` после каждого шага: панель опрашивает `GET /api/v1/jobs/{id}` и показывает этап, прогресс и расходы. Открытие сохранённого результата платных запросов не делает.
