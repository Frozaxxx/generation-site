# Generation Site

Панель, которая генерирует профиль вымышленной B2B-компании, а затем собирает на его основе сайт из трёх страниц.

> **Все компании, люди, адреса и телефоны вымышленные.** Это демонстрационный проект (тестовое задание).
> Телефоны берутся из блоков, которые Bundesnetzagentur зарезервировала для медиапроизводств («Drama Numbers»):
> они совпадают с кодом города, но не выдаются абонентам. Фото команды генерируются моделью.
> Сгенерированные регистрационные сведения не заменяют проверку юрлица в официальных реестрах.

Работа идёт в два этапа:

1. **Компания.** Параметры → генерация → карточка компании (JSON) → ручные правки → утверждение.
2. **Сайт.** Утверждённая карточка + язык (RU/DE) + оформление → версия сайта → предпросмотр и ZIP.

Повторная сборка сайта не генерирует факты заново: единственный источник фактов — сохранённая карточка конкретной ревизии.

## Основной стэк

- `Python 3.14`, `FastAPI`, `SQLAlchemy 2 (async)` + `Alembic`, `Pydantic 2`
- `SQLite` — проект запускается без Docker и внешних сервисов
- `OpenRouter` — тексты и фото команды
- `Jinja2` — шаблон генерируемого сайта
- `React` / `TypeScript` / `Vite` / `Tailwind` — панель (этап 3)

## Запуск

```bash
cd backend
cp .env.example .env          # вписать OPENROUTER_API_KEY
uv sync
uv run python main.py         # http://127.0.0.1:8000/docs
```

Миграции применяются автоматически при старте. Данные лежат в `backend/data/` (в git не попадают).

Через Docker:

```bash
cp backend/.env.example backend/.env   # вписать OPENROUTER_API_KEY
docker compose up -d --build           # http://localhost:8000/docs
```

Данные хранятся в volume `backend-data`.

### Проверка OpenRouter

Один дешёвый запрос: проверяет ключ, модель, разбор JSON и учёт стоимости.

```bash
uv run python -m src.cli check-openrouter                 # модель по умолчанию
uv run python -m src.cli check-openrouter --model openai/gpt-4.1-mini
uv run python -m src.cli check-openrouter --image         # + тестовое фото в backend/data/
```

Проверки:

```bash
uv run pytest
uv run ruff check . && uv run ruff format --check .
```

## Архитектура

Бэкенд разбит на модули, внутри модуля — слои:

```plain
backend/src/
├── core/                  # настройки, FastAPI, база, логирование, миграции
├── shared/                # общие базовые классы: сущности, ошибки, пагинация, репозиторий
├── llm/                   # клиент OpenRouter, лимит расходов, прайс моделей
├── jobs/                  # фоновые задачи генерации: этапы, прогресс, расходы
├── companies/             # этап А: компании и их карточки
│   ├── domain/            # сущность Company, карточка, каталог, проверки согласованности
│   │   └── catalog/       # страны, города, направления, масштабы
│   ├── application/       # сервисы, DTO, протоколы репозиториев
│   ├── infra/database/    # ORM-модели, мапперы, SQL-репозитории
│   ├── dependencies/      # сборка сервисов для FastAPI
│   └── api/v1/            # REST-ручки
└── cli/                   # служебные команды (выгрузка JSON Schema)
```

Правило зависимостей: `api → dependencies → application → domain`, `infra` реализует протоколы из `application`. Домен не знает про FastAPI и базу.

### Генерация компании из терминала

```bash
uv run python -m src.cli generate-company --scale small          # с фото команды
uv run python -m src.cli generate-company --brand "Nordlicht" --no-photos
```

Та же операция доступна в API: `POST /api/v1/companies/generate`, прогресс — `GET /api/v1/jobs/{id}`.

## Как генерируется компания

1. **Факты выбирает код** (`companies/application/generation/facts.py`): город, улица и индекс из каталога, телефон из блока Drama Numbers этого города, домен и почта из названия бренда, год основания и число сотрудников по масштабу, состав команды (руководитель, 2 руководителя отделов, специалисты), имена из пулов разного происхождения, внешность для фото.
2. **Зёрна разнообразия**: история основания, отраслевой фокус, отличие, формат поставки и модель оплаты выбираются случайно. Модели передаются последние созданные компании, чтобы она не повторяла их нишу и формулировки.
3. **Тексты пишет модель** в три шага: концепция и история → продукт и FAQ → биографии команды. Каждый ответ проверяется схемой (количество пунктов, годы этапов, ровно те же люди).
4. **Смысловая проверка**: модель ищет противоречия в продукте, датах и обещаниях; замечания показываются как предупреждения к той ревизии, которую проверяли.
5. **Фото**: единый фон и свет на всю команду, внешность из каталога, промпт против «пластиковой» ретуши; кадр 4:5, 640×800, JPEG без метаданных.

## OpenRouter

- **Ключ** задаётся только на сервере (`OPENROUTER_API_KEY` в `backend/.env`), хранится как `SecretStr`, в ответах API отдаётся только признак «задан / не задан». Фильтр логов и обработка ошибок вырезают ключ из любых сообщений.
- **Модель** выбирается из `OPENROUTER_ALLOWED_TEXT_MODELS`, цены подтягиваются из `GET /models` OpenRouter.
- **Ответы модели** проверяются pydantic-схемой. Невалидный ответ отправляется модели обратно со списком ошибок; это тоже попытка.
- **Повторы** ограничены `OPENROUTER_MAX_RETRIES`: сетевые сбои, 408/429/5xx — с паузой (учитывается `Retry-After`), 401/402/403 не повторяются.
- **Стоимость** берётся из `usage.cost` ответа OpenRouter, при отсутствии — считается по прайсу. Учитываются и неудачные попытки.
- **Лимит на операцию** (`OPENROUTER_OPERATION_BUDGET_USD`): перед каждым запросом проверяется, что потраченное плюс худший случай (входные токены + `max_tokens` по прайсу) укладываются в лимит.
- **Этапы генерации** сохраняются в таблицу `jobs` после каждого шага: панель опрашивает `GET /api/v1/jobs/{id}` и показывает этап, прогресс и расходы. Открытие сохранённого результата платных запросов не делает.

## Карточка компании

Схема: [`docs/company.schema.json`](docs/company.schema.json) (JSON Schema 2020-12), описание полей — [`docs/company-schema.md`](docs/company-schema.md).

Схема генерируется из доменных классов и проверяется тестом на актуальность:

```bash
uv run python -m src.cli export-schema
```
